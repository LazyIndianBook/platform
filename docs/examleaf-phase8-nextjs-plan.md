# ExamLeaf Phase 8 — the Next.js frontend (plan of 2026-10-08)

Founder's decision (2026-10-08): build the decoupled Next.js frontend now, in parallel; the Django-rendered pages will not be used and may be discarded once the new frontend covers them. The assessment that preceded this is in `docs/examleaf-frontend-architecture.md`.

## Boundaries
- **Backend (unchanged ownership)**: `examleaf-web/` Django — REST API v1 (`/api/v1/`), allauth headless (`/_allauth/browser/v1/` for the web, `/_allauth/app/v1/` for the app), the admin (`/admin/`), webhooks (`/shop/webhooks/`, `/anymail/`), health (`/health/`), media (`/shop/media/`, signed storage URLs), the staff clip player (`/learn/preview/`), Google OAuth callback (`/account/google/`), QR PNGs (`/qr/`), the sitemap of Django-only content if any. Business rules, payments, permissions and entitlements stay here; nothing is duplicated in the frontend.
- **Frontend**: `examleaf-frontend/` Next.js (latest stable, App Router, TypeScript, React Server Components), Tailwind CSS v4 with our token layer, shadcn/ui as the customised component foundation, `next/font/local` with the same subset fonts, a typed API client generated from the OpenAPI schema, Playwright and Vitest. Independently developable, testable, buildable and deployable (its own Dockerfile, compose service `frontend`, CI job).
- **One origin**: Caddy serves both under the site domain; requests to the Django prefixes above go to `web:8000`, everything else to `frontend:3000`. Cookies (session, CSRF) are therefore shared: the browser calls `/api/v1/` and `/_allauth/browser/v1/` directly; server components call Django over the internal network with the incoming cookies forwarded and `cache: "no-store"` for anything personal. Public catalogue and content fetches use revalidation (60 s) and tags.
- **Same URL structure as today** so the printed QR codes (`/s/<code>/`), emails (`HEADLESS_FRONTEND_URLS`), search engines and the runbooks keep working: `/`, `/books/<slug>/`, `/s/<code>/`, `/shop/…`, `/cart/`, `/checkout/…`, `/account/…`, `/orders/…`, `/revision/`, `/c/<token>/`, legal pages. Trailing slashes kept (`trailingSlash: true`).
- **Security**: CSP with per-request nonces from Next middleware (`script-src 'self' 'nonce-…' 'strict-dynamic'`, Razorpay only on the pay route, Turnstile only when enabled, `connect-src 'self'` plus the media host, `img-src 'self' data:` plus the media host, `frame-ancestors 'none'`), the other headers as Django sets them; server-side gating of every personal or entitled route (the API decides; the frontend never caches personal data; `Cache-Control: private, no-store` on personalised responses; no personal data in logs or metadata); honest unavailable states; no mock data in production builds.
- **Design system**: the token layer (`docs/design/tokens.css`), component spec (`docs/design/components.md`), motion language (`docs/design/motion.md`) and the Design canvas are the source; shadcn primitives are restyled to them (buttons, inputs, select, checkbox, radio, switch, OTP input, card, badge, alert, toast, dialog, drawer, tabs, accordion, skeleton, table, breadcrumb, pagination, stepper); one icon set (lucide-react, 1.75 px stroke); public pages expressive, account and student pages calm.

## Work packages
- **8A Foundation (first, one builder)**: scaffold, tokens + Tailwind theme + fonts, shadcn components restyled, layouts (public, account, auth), header/footer/toast, typed API client (`openapi-typescript` + `openapi-fetch`) with error normalisation, cancellation, pagination helpers and cache rules, auth layer over allauth headless (session, login by email/phone code, password, passkey, Google start, MFA for staff, sign-up with student details and parental consent, verification by code, password reset, reauthentication), `GET /api/v1/config/` feature flags, pages: home, book, QR landing and solutions (Markdown + maths rendered server-side with KaTeX, print styles), legal pages, about, contact, parent consent `/c/<token>/`, error pages (404, 500, offline), PWA (manifest, service worker, icons), SEO (metadata, canonical, Open Graph, JSON-LD, sitemap, robots, `noindex` on private routes), CSP middleware, Dockerfile (standalone output), compose service, Caddy routing, CI job (lint, type-check, Vitest, build, Playwright smoke), README with setup/env/deploy.
- **8B Shop (after 8A)**: catalogue with categories and collections and attribute filters, product (pictures, attributes, reviews, stock alert, related), cart (offers and coupons), checkout stepper with saved and new addresses, PIN autofill, COD when enabled, pay page with Razorpay checkout.js and confirmation only after the server verifies, order list/detail/token page/lookup, invoices and credit notes download, school quotations.
- **8C Account and revision (after 8A)**: account dashboard, record of attempts (save marks from a solutions page), orders link, details and addresses, phone and passkeys and MFA management, consent state and parent resend, data export and deletion, teacher request, `/revision/` with entitlement, chapters and weights, free preview clips (hls.js), book-code redemption, plan preview; session expiry and intended-destination handling.
- **8D Quality (after 8B/8C)**: Playwright journeys against a seeded Django backend (QR → register → solutions; browse → cart → checkout to the pay page; login by code; account data export), Vitest for components and the API client, accessibility (axe in Playwright, manual keyboard pass), Lighthouse budgets per route on a mobile profile, security review of the frontend (CSP, auth boundaries, caching, leakage), before/after evidence, and the parity check against `docs/design/coverage-matrix.md`.
- **Then**: switch Caddy's default upstream to the frontend, keep Django's pages reachable only through its prefixes, and remove the Django page templates and views in a separate, confirmed clean-up once parity is verified.
