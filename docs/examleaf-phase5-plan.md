# ExamLeaf Phase 5 — real-world production features and the redesign (plan of 2026-10-08)

Inputs: `docs/research/2026-10-08-production-features/report.md` (library and provider verification), `docs/design/resources-brief.md`, `docs/design/direction.md` (the binding design direction and component vocabulary), the Design canvas (16 artboards), `docs/design/components.md` and `docs/design/tokens.css` written from it. Constraints that stay: strict CSP (no inline scripts, self-hosted fonts and scripts), no third-party trackers, minimal personal data (DPDP; many users are minors), mature libraries over hand-written code, every change tested, `check --deploy` clean apart from the two HSTS warnings, migrations in sync, ruff clean.

## Work package A — sign-in and communications (accounts, ops, api)
1. **Phone sign-in with OTP** through allauth 65.19.7's built-ins: `ACCOUNT_LOGIN_METHODS = {"email", "phone"}`, `ACCOUNT_SIGNUP_FIELDS` keeps sign-up email-only (the phone is added later from My account — two codes at sign-up is bad UX), login by code (`ACCOUNT_LOGIN_BY_CODE_ENABLED`, resend), 6-digit numeric code format for SMS and email, the rate limits from the report. New verified fields `User.login_phone` (E.164) and `login_phone_verified` with a partial unique constraint; `IndianPhoneField` normalising "98640 12345" → `+919864012345`; adapter methods `phone_form_field`, `send_verification_code_sms`, `get_user_by_phone` (normalising), `get_phone`, `set_phone`, `set_phone_verified` (un-verify elsewhere); allauth's empty `send_unknown_account_sms` / `send_account_already_exists_sms` kept empty. Templates (login, phone verify, phone change, request/confirm code) overridden on our base template using the component vocabulary. The old free-text `User.phone` stays as contact data only.
2. **Passkeys**: `MFA_SUPPORTED_TYPES` adds `webauthn`, `MFA_PASSKEY_LOGIN_ENABLED = True`, relying-party id = the hostname of `SITE_URL`, `MFA_WEBAUTHN_ALLOW_INSECURE_ORIGIN = DEBUG`, "Use a passkey" button on the login page, passkey management under My account; staff MFA middleware accepts a WebAuthn authenticator as well as TOTP. Passkey sign-up stays off.
3. **Google sign-in**: `allauth.socialaccount` + Google provider with settings-based `APPS` from `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (the provider is listed only when both are set), `SOCIALACCOUNT_AUTO_SIGNUP = False`, a `SocialSignupForm` sharing one mixin with `SignupForm` (class, board, date of birth, parent fields, consent), PKCE on, CSP `form-action` adds `https://accounts.google.com`. The redirect URI and the Google Cloud steps go in DEPLOYMENT.md.
4. **App API**: `POST /api/v1/auth/phone/code/` and `POST /api/v1/auth/phone/confirm/` running allauth's login-by-code process in a throw-away session (as `api/auth.py` does for email codes), same JWT pair on success, generic errors, three attempts per token; documented in API.md.
5. **SMS gateway** `ops/sms.py`: one `send_sms(kind, phone, variables)` Celery task with backends chosen by settings — `console` (default, prints), `msg91` (OTP endpoint `/api/v5/otp?template_id&mobile&otp` and flow endpoint `/api/v5/flow` with template ids from `MSG91_TEMPLATE_<KIND>`), 10 s timeout, retries on transport errors, `SmsLog` table (phone hashed, kind, status, provider id, created) and a database `SMS_DAILY_CAP` (default 500) that refuses sends when exceeded, because the cache-based limits fail open when Redis is down. Order SMS (placed, shipped with tracking, delivered) only to accounts with a verified phone that opted in (`User.sms_updates`), from the existing shop notification path. The founder's DLT checklist (entity, header, templates, URL whitelisting, binding MSG91) goes in RUNBOOK.md.
6. **Parental consent by SMS**: in `PARENTAL_CONSENT_MODE=verified`, `parent_contact` may be a phone; the signed consent link goes by SMS (shortened path `/c/<token>/`), with the DPDP caveat recorded that the delivery channel alone is not a verification route.
7. **Email deliverability**: Amazon SES through Anymail as the documented production backend (`EMAIL_BACKEND=anymail.backends.amazon_ses.EmailBackend`, SES-specific key variables, DKIM/DMARC/MAIL FROM records in DEPLOYMENT.md); `anymail/` webhook URLs protected by `ANYMAIL_WEBHOOK_SECRET`; `EmailSuppression` model fed by the `tracking` signal (hard bounces, complaints, invalid), `pre_send` skips suppressed addresses and cancels empty sends, admin registration so staff can un-suppress; Brevo and Postmark remain selectable through the same settings.
8. **Bot protection**: optional Cloudflare Turnstile (enabled when `TURNSTILE_SITE_KEY`/`TURNSTILE_SECRET_KEY` are set) on sign-up, code request, contact and coupon forms, verified server-side with a 5 s timeout and fail-open logging; CSP gains its script and frame hosts only when enabled.

## Work package B — storage, media, commerce and web platform (shop, content, pages, ops)
1. **Two object storages** in `STORAGES`: `default` = private (answer sheets, invoices, credit notes, quotations; presigned URLs, 300 s), `public` = product images and generated pictures through `PUBLIC_MEDIA_DOMAIN` (immutable cache headers, no query auth). Cloudflare R2 documented as the pick, AWS S3 Mumbai as the India-only alternative for the private bucket; `S3_*` variables separate from SES keys; `AWS_REQUEST_CHECKSUM_CALCULATION` / `AWS_RESPONSE_CHECKSUM_VALIDATION` = `when_required` in compose and `.env.example`; `public_storage()` callable for fields; CSP `img-src` adds the media domain; development and tests keep the filesystem.
2. **Responsive images**: django-pictures 1.8.0 for `Product.cover` and `ProductImage.image` (AVIF + WebP `<picture>`, aspect ratio 2/3 for covers, width/height fields, Celery processor on the default queue), migrations converting the existing fields and re-processing seeded images; the four static covers re-encoded to AVIF and WebP at 320 and 480 px by a build command (`manage.py build_covers`) committed to static, used through `<picture>` in the templates.
3. **SEO**: `{% jsonld %}` tag and JSON-LD for Product+Book (offers, ISBN/GTIN when set, shipping details, return policy), Organization on the home page, BreadcrumbList on product pages; Open Graph and Twitter card tags and `<link rel="canonical">` in base.html; a default OG image plus a per-product 1200×630 composite generated with Pillow on save (Celery) into the public storage; the sitemap kept.
4. **PWA**: `/manifest.webmanifest` view, `/sw.js` rendered per release (precache only static files and the standalone `/offline/` page; never cache HTML, `/account/`, `/shop/`, `/api/`, `/s/`), maskable icons 192/512 generated with Pillow in brand colours, `manifest-src`/`worker-src 'self'` in CSP, registration from the existing self-hosted JS file.
5. **PIN codes**: `PinCode` table built by `manage.py import_pincodes <csv>` from the data.gov.in directory (state mapping to the localflavor codes, districts per PIN), `GET /shop/pin/<pin>/` cached JSON for the address form (vanilla JS autofill of city/district/state), checkout validation only when the table is loaded (state must match the PIN's state), and the founder's download step in DEPLOYMENT.md.
6. **Shipping**: courier choices on `Shipment` with tracking-URL templates (Delhivery, Blue Dart, Ekart; 17TRACK fallback for India Post, DTDC, Xpressbees and others); `ship_order()` fills `tracking_url` when staff leave it blank; the Shiprocket/Delhivery integration shape documented for later, not built.
7. **Reviews**: `Review` (product, user, rating 1–5, text ≤ 1,000, status pending/approved/rejected, history) only from buyers with a delivered order, one per product and user, honeypot and rate limit, admin approval, shown on the product page, `aggregateRating` in JSON-LD only with approved reviews.
8. **School and bulk orders**: `QuoteRequest` (school, contact, GSTIN validated, items with quantities, delivery PIN, note) from a public form with Turnstile when enabled; staff emailed; admin action "Generate quotation PDF" through the WeasyPrint pipeline (valid 15 days, stored in private storage); status field; no payment flow (NEFT/UPI or a Razorpay Payment Link handled by staff and recorded on an order they enter).
9. **Stock**: `StockAlert(email, product)` from the product page when out of stock (double opt-in not needed: one email only when the product returns, then the row is deleted) and a daily low-stock email to the SALES role below `SHOP_LOW_STOCK` (default 5).
10. **GST export**: `manage.py export_gstr1 --from --to` writing the B2C (state and rate), HSN summary and credit-note CSVs from `Invoice`/`CreditNote` for the accountant; documented in RUNBOOK.md.
11. **Supply chain**: `.github/dependabot.yml` (pip weekly, github-actions weekly) and a note on Jazzband's wind-down in DEPLOYMENT.md.

Decided against (recorded here so nobody re-adds them unasked): abandoned-cart emails (marketing to possible minors; DPDP s. 9(3)), third-party analytics (none; server-side counts only if ever needed), site search (nine products and four books), Shiprocket/Delhivery API (volume does not justify it yet), Fast2SMS as a second live backend (one provider interface, MSG91 implemented), WhatsApp OTP (needs a verified Meta business; later), passkey sign-up (later).

Verified at 375 px and 1280 px in the browser, Lighthouse-style checks by hand (no layout shift from fonts, LCP image not animated), tests green.
