# Documentation standard

How every document in this repository is written and laid out, so that the set reads as one work: the same opening,
the same visual vocabulary (badges, callouts, diagrams, tables), the same restraint. It renders the same way on
GitHub and in the documentation portal (`mkdocs serve` from the repository root; `docs/README.md` is the portal's
home). Where a document and this page differ, bring the document to this page.

## 1. The shape of a document

Every document opens the same way, in this order:

1. **The title** (`#`), a noun phrase naming the thing, never a sentence: "Deployment", "The staff API", "Runbook".
2. **The badge row**: one line of local badges (section 3) that say what the reader most wants to know before reading:
   the component, the phase or status, the test count, the audience. Three to five badges; never more than six.
3. **The lead**: one paragraph, two to four sentences, saying what the document is for and who reads it.
4. **At a glance** (a `> [!NOTE]` callout, section 4): the three to six facts a reader takes away if they read nothing
   else, as a short list.
5. **Contents** for a document over about 200 lines: a bullet list of its `##` sections with links.
6. The body: `##` sections, `###` subsections, never deeper than `###`.
7. **Related documents** at the end: the four to eight documents a reader goes to next, with one phrase each.

Long reference tables (more than about 25 rows) go inside a `<details>` block with a `<summary>` naming what it holds
and how many rows, so the page stays navigable; the first rows a reader needs most come first.

## 2. Prose

British English; sentences, not fragments; the present tense; "the panel", "the website", "the backend" as the
documents already say them. No emoji, no exclamation marks, no marketing. Code, paths, settings and commands in
backticks; a command on its own line in a fenced block, one command per block. A number with a unit or a count goes
in a table or a badge, not in a sentence, unless the sentence is about that number.

## 3. Badges

Badges are local SVG files in `docs/assets/badges/`, generated by `scripts/docs/badges.py` from `badges.json` beside
them (regenerate after changing the facts; never link an external badge service: the documents must render offline
and never call out). A badge row is one Markdown line of images, each linked where it helps:

```markdown
![Component](../docs/assets/badges/component-backend.svg)
![Phase](../docs/assets/badges/phase-b-merged.svg)
![Tests](../docs/assets/badges/tests-backend.svg)
```

Badge families and their colours: `component-*` (slate), `phase-*` and `status-*` (green for done or merged, amber
for pending, red for blocked), `tests-*` (blue), `audience-*` (violet), `law-*` (teal, a legal deadline or statute).
Add a badge by adding its entry to `badges.json` and running the script; never hand-edit an SVG.

## 4. Callouts

GitHub's alerts, which the portal renders as admonitions. Use each for one purpose only:

| Callout | Use |
|---|---|
| `> [!NOTE]` | "At a glance" boxes, facts worth knowing, where a value comes from |
| `> [!TIP]` | the shorter way, the command that does it, a recommended setting |
| `> [!IMPORTANT]` | a rule the reader must follow: the one rule, a guardrail, a legal duty |
| `> [!WARNING]` | something that goes wrong when skipped: data loss, a lock-out, money |
| `> [!CAUTION]` | the break-glass line in the RUNBOOK ("If the panel is down"), destructive commands |

A callout is three lines at most. The first line may be bold and name the point.

## 5. Diagrams and charts

Mermaid, in a ```` ```mermaid ```` fence, rendered by GitHub and the portal alike. Draw a diagram when the prose
describes a flow, a lifecycle, a topology or a timeline; never decorate. One diagram answers one question and has a
one-line caption below it in italics. Keep each under about 25 nodes; split a bigger one by concern.

| Kind | Mermaid | When |
|---|---|---|
| Architecture, routing, decisions | `flowchart LR` or `TB` | who talks to whom, which path a request takes, a decision with branches |
| A lifecycle | `stateDiagram-v2` | an order's, a job's, a change request's, a ticket's states and transitions |
| A conversation across systems | `sequenceDiagram` | a webhook, the approval of a change, an impersonation, the ERPNext outbox |
| Records and their links | `erDiagram` | a module's main models, five to ten entities |
| A plan over time | `gantt` or `timeline` | phases, deadlines the law sets, a migration |
| Numbers | `xychart-beta` (bars, lines) or `pie` | test counts by phase, findings by severity, a split worth seeing |
| A map of a subject | `mindmap` | the documentation map, a module's parts |
| The merge history | `gitGraph` | how branches came together |

Conventions: `flowchart LR` for systems left to right, `TB` for decisions top to bottom; label every edge that carries
a condition; name nodes as the documents name them (the panel, the website, Django, ERPNext, Razorpay); no colours
beyond the theme (Mermaid's `classDef` is allowed for one highlighted node). Every diagram passes
`python scripts/docs/check_mermaid.py` (it renders each fence with the Mermaid command line and fails on a syntax
error); run it before committing.

The documentation portal adds a hero diagram of the platform (`docs/assets/platform-flow.svg`, drawn by hand with a
subtle animation of the data flow); nothing else moves.

## 6. Tables

A table for anything with three or more comparable items. The first column names the item in backticks when it is a
path, a setting or a permission; the last column says what it is for in a phrase. Align nothing by hand (the
renderer does); keep a row to one line of source where it can be. A matrix (roles × modules, endpoints × permissions)
uses one character per cell: `yes`, `read`, a blank, never a symbol.

## 7. Navigation

Every document is reachable from `docs/README.md` (the documentation map) within two clicks and names its neighbours
in "Related documents". Headings keep their anchors: other documents link to them, and the portal's search does too.
A heading is renamed only with every link to it (grep first). A long document opens with Contents.

## 8. What stays as it is

The generated parts (the staff API reference in `API.md` between its markers, `openapi.json`, the schema types) are
never edited by hand. The research reports under `docs/research/` and the test papers under
`examleaf-web/content/fixtures/` are archives: an opening badge row and a lead are enough. The CHANGELOG keeps its
entries verbatim; its opening gains the summary table and the timeline.

## 9. The portal

`mkdocs serve` builds the documentation site from the same files: `scripts/docs/build_site.py` gathers every document
into `.docs-build/`, rewrites the links between them, turns GitHub's alerts into admonitions and writes the
navigation from `docs/nav.yml`; `mkdocs.yml` holds the theme (Material: light and dark, search, the navigation
tabs, instant loading), the Mermaid fence and the stylesheet `docs/assets/css/extra.css` (the brand palette, the cards
on the home page with their hover, the badge row's spacing). `make docs` builds it into `site/` (ignored by git); CI
builds it on every change to a document and keeps it as an artifact.
