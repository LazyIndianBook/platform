# Resilience: the staff console

What keeps `examleaf-admin` answering when Django is slow, hung or gone, what keeps one process up, and why any number
of them can serve one person. Checked on 9 October 2026 against Next.js 16.4.0 and React 19.3, as the public site was
(`../examleaf-frontend/RESILIENCE.md`, which explains the two leaks at length): each item verified in the code, fixed
where it failed, then proven on a production build (`next build`, the standalone `server.js` as the image runs it)
under load against a stub Django.

## The load proof

Each run: 50 keep-alive connections for 60 s to `/sign-in/` (the console's one page that needs no session; it asks
Django for the config on every view), from a Node script with no dependency; the standalone `server.js` with the
image's `--max-old-space-size=384` and `KEEP_ALIVE_TIMEOUT=125000`; a stub Django on the same machine, with modes that
hang everything or the API alone. The machine: an 8-core laptop shared with other work, Node 20.19 (the image runs
Node 24). The heap is V8's `heapUsed` at the run's first sample, its peak and its last; the RSS is macOS's.

at most 81 MB): a kept connection to Django was one of the things that held the chain of requests, and there are
others, so the fix is at the chain (`src/instrumentation.ts`).

## Graceful shutdown, keep-alive

As on the public site: on SIGTERM the server stops listening at once, finishes the requests it has (10 s at most) and
exits 143; `/api/health/` answers 503 from then on. The chart gives the preStop plus 20 s. Docker Compose kills a
container 10 s after SIGTERM by default, the deadline itself: `stop_grace_period: 15s` on the admin service lets the
last request finish. The image's keep-alive (125 s) is longer than Traefik's (90 s) and Caddy's (2 minutes), so the
proxy closes an idle connection first.

## The operator's knobs

| Knob                      | Where                                  | Default                    | What it does                                                                                                        |
| ------------------------- | -------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `API_INTERNAL_TIMEOUT_MS` | environment                            | 10000                      | How long one request may wait on Django in all. Raise the grace period with it.                                     |
| `NODE_OPTIONS`            | environment (the image's)              | `--max-old-space-size=384` | The heap limit: about 75 % of the memory limit (576 for 768Mi, 768 for 1Gi): `admin.env.NODE_OPTIONS` in the chart. |
| `KEEP_ALIVE_TIMEOUT`      | environment (the image's)              | 125000                     | Longer than the proxy keeps an idle connection (Traefik's `idleConnTimeout`, Caddy's `keepalive`).                  |
| `ANSWER_TIMEOUT_MS`       | `src/lib/api/client.ts`                | 30 s                       | How long the browser waits for an answer.                                                                           |
| `AGAIN_S`                 | `src/components/data/job-progress.tsx` | 10 s                       | How soon a job's progress asks again after no answer or a server error (or after a 429's wait, if longer).          |
| The health cache          | `src/proxy.ts`                         | 5 s, 2 s                   | How often pages ask `/health/web/`, and how long they wait for it.                                                  |

## Deferred

- **A change that timed out, pressed again.** The words say to check first, but the staff API takes no idempotency
  key, so a second press can make a second invite, job or note.
- **429 wording.** allauth's rate limits come with no `Retry-After`, so the sign-in form says to wait without saying
  how long.
- **A failed page without script.** Next 16 draws `error.tsx` after hydration: with script off, a page that failed
  shows no words. The proxy's 503 is self-contained.
- **A body cut off after the headers** of a 200 in allauth's browser client (`src/lib/auth/headless.ts`) reads as "not
  signed in": rare (Django writes whole answers), and bounded by the 30 s.
- **The four static pages and the policy.** `/inactive/`, `/no-access/`, `/set-up-two-step/` and the root 404 read
  no session, so `next build` prerenders them, and their scripts carry no nonce (13 script tags on `/no-access/`, none
  with one). The proxy serves them under `script-src 'self' 'nonce-…' 'strict-dynamic'`, where browsers ignore
  `'self'`: none of their scripts runs, so the Sign out of `/no-access/` and `/set-up-two-step/` does nothing and the
  404 gets no focus handling (`next dev`, where the end-to-end suite runs, renders every page per request and hides
  it). Found as this work closed; the fix keeps the policy and renders them per request, as the root layout's comment
  already assumes: `await connection()` in the root layout.
- **The abort wrapper** (`src/instrumentation.ts`) works around React and Node: remove it once React stops leaving
  that Error or Node unlinks a run Immediate, and run the sign-in load again to see.
